电力用户用电信息采集系统的面向对象协议，也就是 DLT698.45 的主站-终端通信部分。和老协议 DL/T645 的"读数据标识"思路完全不同，第一次接触容易懵。

## 帧结构概览

一帧完整的 698 报文长这样：

```
68 L L 68 [控制域 C] [地址域 A] [帧头校验 HCS] [链路用户数据] [帧校验 FCS] 16
```

| 域 | 长度 | 说明 |
| --- | --- | --- |
| 起始符 | 1 B | 固定 `0x68` |
| 长度 L | 2 B | **低字节在前**，且 D0 是分割标志 |
| 控制域 C | 1 B | 方向、功能码、分帧标志 |
| 地址域 A | 可变 | 服务器地址 + 客户机地址 |
| HCS | 2 B | 从控制域到地址域结束的 CRC16 |
| 链路用户数据 | L 指定 | APDU，真正的应用层内容 |
| FCS | 2 B | 整帧 CRC16 |
| 结束符 | 1 B | `0x16` |

### 长度域的坑

长度 L 是两个字节，但有效位只有 14 bit：

```c
uint16_t len_raw = (frame[2] << 8) | frame[1];   /* 注意字节序 */
uint16_t userdata_len = len_raw & 0x3FFF;        /* 低 14 位有效 */
uint8_t  segmented    = (len_raw >> 15) & 0x01;  /* 最高位是分帧标志 */
```

`0x8000` 那一位不是长度的一部分，是分帧标志。看过 645 的人容易直接当成 16 位长度用，结果收到长帧时解析错位。

## 对象标识 OI

698 里所有数据都是"对象"，用 **OI（Object Identifier）** 标识，4 字节。

```
OI = 0x00100200
     └┬┘└┬┘└┬┘
      │  │  └─ 属性索引（低字节）
      │  └──── 对象编号
      └─────── 对象分类
```

在终端固件里通常这么组织：

```c
typedef union {
    uint32_t value;
    struct {
        uint8_t attr;      /* 属性/方法索引 */
        uint8_t index;     /* 对象编号低字节 */
        uint8_t mid;       /* 对象编号高字节 */
        uint8_t cls;       /* 分类 */
    } f;
} oi_t;
```

解析时先按 `cls` 分大类，再在类内查表找 `index + mid` 对应的处理函数。表驱动比 switch 好维护，尤其一个对象动辄几十个属性的时候。

## 数据类型编码

APDU 里的数据用 **Data** 类型，第一个字节是类型标签：

| 标签 | 类型 | 长度 |
| --- | --- | --- |
| `0x00` | NULL | 0 |
| `0x01` | array | 后跟元素个数 |
| `0x02` | structure | 后跟成员个数 |
| `0x03` | bool | 1 |
| `0x05` | double-long | 4 |
| `0x06` | double-long-unsigned | 4 |
| `0x09` | octet-string | 后跟长度 |
| `0x0A` | visible-string | 后跟长度 |
| `0x0C` | OI | 4 |
| `0x10` | long | 2 |
| `0x11` | unsigned | 1 |
| `0x12` | long-unsigned | 2 |

注意 `0x11` unsigned 是 **1 字节**，`0x12` long-unsigned 是 **2 字节**——和 C 语言的直觉不一样，容易搞反。

```c
int data_decode(const uint8_t *buf, int len, data_value_t *out)
{
    uint8_t tag = buf[0];

    switch (tag) {
    case DT_UNSIGNED:               /* 0x11 */
        out->u32 = buf[1];
        return 2;                   /* tag + 1 字节 */
    case DT_LONG_UNSIGNED:          /* 0x12 */
        out->u32 = (buf[1] << 8) | buf[2];
        return 3;
    case DT_DOUBLE_LONG_UNSIGNED:   /* 0x06 */
        out->u32 = (buf[1] << 24) | (buf[2] << 16) | (buf[3] << 8) | buf[4];
        return 5;
    /* ... */
    }
    return -1;
}
```

**多字节一律大端（网络序）**，这点和 645 的逆序字节序正好相反。

## 与 DL/T645 的转换

645 是"数据标识 DI + 数据域"的两层结构，698 是"OI + 属性"的面向对象结构，两者不是简单映射。

常用的映射表：

| 645 数据标识 | 含义 | 698 OI |
| --- | --- | --- |
| `00000000` | 组合有功总电能 | `00100200` |
| `00010000` | 组合无功总电能 | `00200200` |
| `02010100` | 电压（A 相） | `20000200` |
| `02020100` | 电流（A 相） | `20010200` |

实际转换时有几个坑：

1. **字节序相反**。645 的数据域是低字节在前，698 是大端，转换时必须翻转
2. **BCD vs 整型**。645 大量用 BCD 码，698 用整型，要做码制转换
3. **精度不同**。645 电能值常见 `XX.XXXX`（4 位小数）的 BCD，698 里可能是缩放因子 + 整数，需要额外处理量纲

## 探测帧

主站常发探测帧判断终端是否在线。两种常见形式：

- **FC03**：读保持寄存器（Modbus 语义借用）
- **FC0D**：有些厂家自定义的自定义探测

严格来说这不是 698 标准的一部分，是现场实现的惯例。终端侧要能识别并回应，否则会被判定离线。

## 调试建议

解析类代码的调试，我的习惯是：

1. **先把原始报文 hex dump 出来**，确认收全了、没被 UART 截断
2. **逐段校验**。先校 L 域，再校 HCS，最后 FCS。HCS 错了就不用往下解了
3. **保留解析失败时的原始帧**，别直接丢掉。现场问题复现成本高，留下一帧原始数据比事后猜强

```c
/* 校验失败时把整帧打出来 */
static void dump_failed_frame(const uint8_t *buf, int len)
{
    rt_kprintf("[698] bad frame, len=%d: ", len);
    for (int i = 0; i < len; i++)
        rt_kprintf("%02X ", buf[i]);
    rt_kprintf("\n");
}
```
